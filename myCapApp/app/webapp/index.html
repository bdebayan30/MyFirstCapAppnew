SHEET 01

What CAP actually is

CAP isn't a single library — it's a set of tools, languages, and generic implementations that turn a domain model into a running, cloud-ready service. You write intent; CAP writes boilerplate.

◈

Core Data Services (CDS)

A single modeling language for data, services, and UI annotations — the one source of truth every layer reads from.

⬡

Generic providers

CRUD, drafts, search, pagination, and authorization come out of the box — no handwritten controllers required.

◧

Polyglot runtimes

The same model runs on Node.js or Java. Pick the runtime that fits your team, not one CAP forces on you.

SHEET 03

CDS: the data model

A CDS file reads like a schema, but it's really the contract every other layer builds on. Here's a minimal bookshop model — two entities and the association between them.

db/schema.cds
namespace sap.capm.bookshop;

entity Books {
  key ID     : UUID;
      title  : String(120);
      stock  : Integer;
      price  : Decimal(9,2);
      author : Association to Authors;
}

entity Authors {
  key ID    : UUID;
      name  : String(111);
      books : Association to many Books
              on books.author = $self;
}

Why this matters

  • One definition, many consumers. The same entity feeds the database schema, the OData API, and Fiori annotations.
  • Associations, not foreign keys. CDS expresses relationships at the model level; CAP resolves the joins.
  • Reuse via aspects. Common fields like managed or cuid mix into any entity.
SHEET 04

Services: expose and refine

A service definition picks what to expose. Custom handlers refine it — CAP calls yours before or after its own generic logic, so you only write the exceptions to the default behavior.

srv/catalog-service.cds
using sap.capm.bookshop as my from '../db/schema';

service CatalogService {
  entity Books   as projection on my.Books;
  entity Authors as projection on my.Authors;
}
srv/catalog-service.js
module.exports = async function(srv) {

  // runs before the generic CREATE handler
  srv.before('CREATE', 'Books', req => {
    if (req.data.stock < 0)
      req.reject(400, 'Stock cannot be negative');
  });

  // runs after the generic READ handler
  srv.after('READ', 'Books', books => {
    for (const b of books) b.available = b.stock > 0;
  });
};
CatalogServiceHandler.java
@Component
@ServiceName("CatalogService")
public class CatalogServiceHandler implements EventHandler {

  @Before(event = CqnService.EVENT_CREATE, entity = "Books")
  public void validateStock(Books book) {
    if (book.getStock() < 0)
      throw new ServiceException("Stock cannot be negative");
  }
}

SHEET 07

For the conventional ABAP developer

CAP isn't a foreign world — it takes patterns an ABAP developer already knows from SE11, SE80, and RAP, and expresses them in a leaner, cloud-native syntax. The mental model transfers; the tooling changes.

◈

The biggest shortcut: CDS is the same language. ABAP CDS views inside S/4HANA and the CDS used in CAP share the same underlying modeling language and much of the same annotation vocabulary. Time spent writing @AbapCatalog or association syntax in ABAP CDS is not wasted — it's the same muscle memory, just without a backend system attached.

ABAP worldCAP equivalentWhat changes
DDIC table / structure (SE11) CDS entity (schema.cds) Fields and keys are declared the same way — just in a plain text file instead of a GUI transaction, and versioned in git rather than a transport.
ABAP CDS view + associations CAP CDS entity + associations Nearly identical syntax for joins and relationships — the biggest conceptual leap has often already been made if you've written ABAP CDS.
RAP behavior definition Service definition + event handlers Both separate "what's exposed" from "what happens on create/update" — RAP's determinations and validations map to CAP's before/on/after hooks.
BAdI / user-exit srv.before() / .on() / .after() Same idea — hook in before or after standard processing — but registered in a few lines of code instead of an enhancement spot.
Whitelisted BAPI / RFC OData / REST service CAP generates the API from the model automatically, rather than you hand-building and releasing an interface.
SE80 / ABAP Development Tools VS Code + cds CLI Autocomplete, syntax checks, and a local test server (cds watch) replace the ABAP Workbench — no backend system required to start coding.
Transport requests (SE09/SE10) Git commits + CI/CD pipeline Change tracking moves from transport layers to standard version control, which plugs into any CI/CD tool.
SAP GUI screen / dynpro Fiori Elements page (from annotations) UI is generated from CDS annotations rather than laid out field-by-field — you describe intent, not pixels.

Where the effort actually goes

  • Syntax, not concepts. Domain modeling, separating interface from implementation, and hooking into a request lifecycle are all things ABAP already trained you to do.
  • New muscle: JavaScript or Java basics. Custom handler logic is written in Node.js or Java — the biggest genuinely new skill for a classic ABAP developer.
  • Old muscle: CDS modeling. If you've written ABAP CDS views with associations and annotations, that knowledge carries over almost directly.
  • Career angle. SAP is steering S/4HANA extensions toward CAP and RAP together — learning CAP is learning the same declarative pattern SAP now expects everywhere, on and off the ABAP stack.
SHEET 08

Why teams reach for CAP

Not because it's the only way to build a backend — because it removes the parts of enterprise software that don't differentiate your product.

01

Best practices, built in

Multitenancy, extensibility, and internationalization are default behavior, not add-ons you assemble yourself.

02

Grow into complexity

Start with an in-memory SQLite database, move to HANA Cloud later — the model doesn't change.

03

Fiori for free

Well-annotated services power Fiori Elements list and object pages with no extra UI code.

04

Testable by design

Generic providers are already tested by SAP; your handlers stay small enough to unit test easily.
